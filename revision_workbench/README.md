# Thesis revision 工作台

在仓库根目录双击 `START_HERE.html`。页面和所需数据都在本地，不需要安装依赖或联网。历史只读 reader 原样保留在 `revision_workshop_20261031_v5/reader/index.html`。

## 每次使用

1. 首次打开直接开始；如果换了浏览器、路径或电脑，先导入上次导出的 JSON 记录。
2. 按原 report 顺序查看：Benetos 在前，奥克兰大学教授在后。每条都有原意见、作者原回复、助手建议和具体源码位置。
3. 在“作者决定”里选择“修改 / 不修改 / 待定”，填写“修改计划 / 留言”和“实际修改文字”。英文与 LaTeX 保留原样。
4. 留意页面的保存状态；结束前点击“导出 JSON 备份”，把带时间戳的新文件存到自己的备份目录，保留此前的备份。下次导入可合并已有记录，不会整份覆盖旧记录。

浏览器自动保存只服务于当前浏览器的本地环境。`file://` 页面的保存行为取决于浏览器；移动网页、换浏览器、清理浏览器数据或换电脑后，旧记录不保证自动出现。**JSON 文件才是可携带备份**。页面不提供跨浏览器或设备同步，不自动写回论文，也不会自动上传或推送你的笔记。

每次导出生成新的 JSON 下载文件，不连接或改写已有备份。请确认浏览器已经完成下载，不要用新文件覆盖唯一的旧备份；多个标签页各自导出时，也分别保留并合并导入。页面不会静默写入磁盘文件。

如果浏览器阻止本地页面保存，可以在仓库根目录运行 `python3 -m http.server 8000`，再打开 `http://localhost:8000/START_HERE.html`。这会形成另一个浏览器保存环境；先导出旧环境，再在新环境导入。没有 Python 也仍可直接双击 HTML，并用 JSON 导入/导出保存。

## 两个决定与颜色

每列都是互斥的三个选项。“作者决定”的预填只来自原报告 PDF 里有明确意思的作者批注，页面同时展示原话、PDF 页码与批注编号；未回复、混合意见、技术解释或意思不明确的仍是待定。预填只表达是否需要处理该问题，不批准后来生成的具体英文或候选路线。

| 助手建议 | 作者决定 | 显示状态 |
| --- | --- | --- |
| 修改 | 修改 | 绿色：双方同意修改 |
| 不修改 | 不修改 | 红色：双方同意保留 |
| 不修改 | 待定 | 灰色：助手建议保留，作者待定 |
| 其他组合 | 其他组合 | 黄色：待定或意见不一致 |

颜色有对应文字。红色表示双方同意保留，不是错误。双方同意修改也不表示已经修改：计划、实际文字与执行/核验状态分别保存。导出的报告会保留待定和未核验标记，不能把勾选直接变成“已修订”的声明。

## 保存、冲突与恢复

每个字段分别追加保存，旧标签页不会用整份旧记录覆盖新记录。不同标签页同时编辑同一个字段时，冲突版本会保留下来，需明确选定或合并；不要在未检查冲突前假设页面已保存最终稿。导入 JSON 同样保留版本和来源，不会丢弃未知的条目 ID。页面若报告浏览器存储不可用或损坏，请立即导出可恢复记录，并保留原 JSON 备份。

如果浏览器中的保存项丢失或损坏，当前页仍能恢复的记录会保留在内存并提示；先导出备份，再点“重试浏览器保存”。修复前的损坏原始数据也会归档保留；这不能恢复从未被当前页面读到、也没有备份的数据。

如果某次输入未通过保存校验，页面不会显示为已保存。不要刷新或关闭；立即点“救出未保存文字”，下载保留原字的独立草稿 JSON。常规 JSON 备份也包含这些 `uncommittedDrafts`；它们仍是未提交草稿。独立救出文件不是完整 ledger，不直接作为正式记录导入，可据此逐字恢复或交回整理。如果总备份超出导出大小限制，页面会明确报失败并保留现有记录；先救出未保存文字，保留已有 JSON，再分批整理。

助手建议或候选文字更新后，旧选择仍保留；涉及不同候选版本的选择需要重新确认。浏览器保存、导入合并、撤销都不授权修改论文。将来整理 revision report 时，交回导出的 JSON 即可。

执行状态和核验记录还绑定当时的建议、来源和“实际修改文字”。实际文字或来源变化后，旧的“已修改 / 已核验”记录留在历史里，当前状态先回到“尚未执行”，需重新检查后记录，不能让旧核验替新文字背书。

原回复中只针对某个范围的明确决定会单独显示。例如 R1-21 已勾选“不扩展当前项目”，它不等于拒绝补写论文说明，因此整条论文修改决定仍待定。可选小修也单独选择，不随另一条意见的同意自动采用。

## 开发与验证

所有运行资源均为仓库内文件，无 CDN、云端后端或密钥。构建与测试使用 Python / Node 的标准库。

- `python3 revision_workbench/build.py`：把数据、样式和脚本嵌入根目录的 `START_HERE.html`。
- `python3 revision_workbench/verify_sources.py`：核对 421 个原有文件的 SHA256，确保论文、报告和历史材料没有被改写；允许根目录 `README.md` 与 `.gitignore` 的入口/备份排除说明更新，并单列这些变更。
- `python3 revision_workbench/verify_sources.py --data revision_workbench/data.json`：额外核对 43 条意见的顺序、源码相对路径、行号、原文引句、嵌入上下文及作者回复出处；作者 PDF 批注的页码、编号、原话与 PDF SHA256 逐项对应源审计文件。测试夹具不能通过交付验证。
- `node revision_workbench/tests/ledger.test.cjs`：验证持久化、冲突和导入导出。
- `node revision_workbench/tests/browser.mjs`：运行真实浏览器集成测试，需要带内置 WebSocket 的 Node 及本机 Chrome。Mac 默认使用 `/Applications/Google Chrome.app`，其他路径可设 `CHROME_PATH`。测试与截图在 `revision_workbench/tests/` 和 `revision_workbench/evidence/`；使用隔离测试 profile，不写入正常浏览器的作者记录。

`source_baseline.json` 固定于远端基线 `b2995d0aa9ddcb47532a47bcd326f6200fc7b12a`。验证器只读，不会修改源码或重新生成基线。

## 下次论文 revision 复用

通用入口的数据配置支持任意 reviewer 名称和意见数量。按 [DATA_CONTRACT.md](DATA_CONTRACT.md) 的最小流程复制核心文件，将 [reusable.template.json](reusable.template.json) 填为新稿的 `data.json`，再构建根目录入口。每篇稿件使用独立且稳定的 `documentId`；同一稿件的版本更新保留此 ID 和 comment ID，候选变化另更新内容 hash。不同稿件的 JSON 不互相导入，不靠改 ID 强行合并。

源码更新后，构建器会核对原句和 hash：能唯一确认的位置才重新定位，缺失或有歧义的保留待人工处理。原始位置与用户文字不改写；来源或候选版本变化后，旧决定需要重新确认。自定义数据、输出和源码根目录可使用构建参数 `--data`、`--output`、`--source-root`，详见数据约定。

模板明确标为占位数据，没有任何真实作者选择。Thesis 的 43 条映射及来源验证继续独立保留。设计概念与上游许可证说明见 [OPEN_SOURCE_DESIGN.md](OPEN_SOURCE_DESIGN.md)；页面运行没有新增第三方依赖。
